- Setup (validated in the earlier `run smoke` run): optional Mac-path symlink recreated via `sudo`; `pip install numpy==2.2.6 scipy scikit-learn matplotlib torch==2.14.0` — all of these were **already installed** in this container from the smoke run (persisted state), so no fresh install was needed this run; versions confirmed identical to the smoke report (`numpy 2.2.6, scipy 1.17.1, scikit-learn 1.9.1, torch 2.14.0+cu130, matplotlib 3.11.2`). ## 3. Results (seed, floor, last-significant depth, anomalous recovery)

Full per-depth detail (23 depths x 12 seeds = 276 rows, plus header) is in `results/rf_floors_101-112.csv`, with columns `seed, depth_cm, real_acc, p_value_raw, p_value_bh_adjusted, fdr_significant, floor_cm, last_significant_cm, anomalous_recovery, train_seconds, controls_seconds, eval_seconds, total_seconds`.

**`p_value_bh_adjusted` is a derived quantity, not a number `lane8_harness.py` computes.** The unmodified harness's `bh_fdr_correction()` (imported unchanged from `Source/degradation_aware_final_sweep.py`) returns only a boolean significant/not-significant flag from the classic Benjamini-Hochberg step-up procedure, never a numeric adjusted p-value (q-value). Since the task asks for "BH-adjusted p" in the results CSV, the wrapper computes the standard BH q-value transform itself from the harness's own raw per-depth p-values (`audit_fixes/cloud/rf/run_rf_seeds.py::bh_adjusted_pvalues`), and this is disclosed rather than silently presented as if the harness produced it. `fdr_significant` in the CSV is still the harness's own flag, unedited.

**Two findings flagged, not smoothed over:**

- **Seed 106: anomalous recovery.** `anomalous_recovery_rf = True` because a *later*, deeper depth (13.6364 cm) came back FDR-significant after an earlier, shallower depth (12.2727 cm, the reported floor) had already failed to reach significance — i.e., accuracy did not degrade monotonically with depth for this seed's RF fit. This is the harness's own unmodified logic (`any(sig and depth_cm > floor_cm for depth_cm, sig in zip(depths, sig_flags))`) surfacing a real non-monotonicity in this seed's per-depth eval, not a bug introduced by the wrapper. Reported as-is.
- **Seed 110: floor pinned at the grid ceiling (15.0000 cm).** `EVAL_DEPTHS_CM`'s maximum value is 15 cm; when every depth up to and including the last one is FDR-significant, `lane8_harness.run_one_seed` falls back to `depths[-1]` (see `lane8_harness.py` lines 124-125, unmodified) rather than reporting "no floor observed within the tested range." That is a real, disclosed limitation of the *unmodified* harness's floor convention (not something this wrapper introduced): a floor of exactly 15.0000 cm is indistinguishable, from this CSV alone, between "the true degradation floor is exactly at the grid edge" and "the true floor is beyond the grid and was never tested." The per-depth detail rows for seed 110 in `results/rf_floors_101-112.csv` should be checked directly if this distinction matters for downstream analysis.

## 4. Flaws / deviations surfaced (including in these requirements)

1. **Tension between "never edit files under `audit_fixes/lane8`" and the harness's own hardcoded output paths.** `lane8_harness.run_one_seed()` unconditionally writes `audit_fixes/lane8/logs/lane8_depth_detail_seed{seed}.csv` on every call (`LOG_DIR`/`CSV_PATH` are hardcoded relative to `lane8_harness.py`'s own location, not configurable). Those files are tracked in `<base>`'s history from the earlier smoke run (only seed 101 existed there); running seeds 102-112 through the unmodified harness necessarily wrote 11 new per-seed detail CSVs into that directory as a side effect of code we are forbidden to edit. Resolution adopted this run: after copying each seed's needed data (per-depth accuracy, raw p) into `results/rf_floors_101-112.csv`, the side-effect file was deleted from the working tree (untracked new files) or `git checkout --`'d back to its last-committed content (the one pre-existing tracked file, seed 101's) — never staged or committed. This keeps `audit_fixes/lane8/` literally unedited in git history on this branch, at the cost of discarding the harness's own duplicate copy of data already preserved elsewhere. `lane8_run.log` (a single shared, append-mode log file across the whole run) was also repeatedly reset this way; some of its content written during active appends may have been lost to the reset rather than committed, since it is not needed for the results and committing it would violate the "never edit" rule. This is a structural gap in the run requirements, not an error introduced this run: if lane8's outputs must never be touched, the harness itself should not hardcode writes into that directory, or the requirements should explicitly say those side-effect files are exempt from "never edit."
2. **Same undeclared `matplotlib` dependency as the smoke run.** Not re-encountered as a failure this run only because it was already installed from `run smoke`; still worth fixing at the source (`Source/physics_model.py` imports `matplotlib.pyplot` at module scope purely for an unused plotting capability in Lane 8's import chain).
3. **No numeric BH-adjusted p-value in the pre-registered pipeline.** As detailed in section 3, `bh_fdr_correction()` only returns a boolean flag. The task's request for "BH-adjusted p" in the output CSV required computing this independently in the wrapper; this is disclosed as a derived, not harness-native, number.
4. **The split (101-112 / 113-124) is not itself checkpoint/resume-aware across runs.** `run_rf_seeds.py`'s resume logic only looks at `results/rf_floors_<start>-<end>.csv` for its own `--start/--end` range; a run covering 113-124 will write a separate file (`results/rf_floors_113-124.csv`) and will not know about or validate against this run's output. Combining both into one 24-seed dataset (for the PREREG.md section 7 analysis) is left as a manual step for whoever runs that analysis, not automated here.
5. **10-minute poll cadence vs. burst completions.** Because the harness prints its `SEED_DONE` line only once a seed fully finishes (~470-515s), and the poll loop checked every 600s, two seeds occasionally finished within one poll window and only the most recent line was caught by a naive `tail -n 2`; this was caught and corrected mid-run by switching to `grep -E "SEED_DONE|Traceback|Error"` over the whole log rather than a fixed-line tail, and cross-checked against `git log origin/<branch>` after every event to confirm no checkpoint was silently missed. No seed's checkpoint commit was actually missing at any point — this was a monitoring-script gap, not a data gap — but it's recorded here since the protocol is to surface every flaw encountered, including transient ones in this run's own tooling.
6. **Stop-hook vs. "never edit lane8" recurring conflict.** The repository's local stop hook (a local git check script) fires on any uncommitted/untracked change, including the lane8 side-effect files from point 1 above. Since committing those files would violate the explicit task rule, each occurrence was resolved by discarding/deleting the lane8-side files (never committing them) and only committing the wrapper's own log files under `audit_fixes/cloud/rf/logs/`. This recurred after nearly every seed for the entire run and is a structural mismatch between the hook's "nothing uncommitted, ever" policy and this task's "don't touch this directory" policy — flagged rather than silently worked around.
